# POC 角色能力与验收边界

更新：2026-09-22。本文把 [v0.3 设计](design-v0.3.md) 的职责落实为能力合同，供定位问题和设计测试使用，不增加新的 Agent 或运行时层级。当前实现状态以代码和实机证据为准，设计中的动作枚举不等于已经实现的能力。

## 1. 谁负责什么

只有一个本地 AgentLoop、一套本地模型实例。Kimi、豆包、DeepSeek 是外部业务参与者，不是三个本地控制 Agent。

| 角色 / 代码位置 | 输入 | 负责输出 | 不拥有的权限 / 职责 | 当前状态 |
|---|---|---|---|---|
| 用户 / `ui/` | 原始目标、参与者、总结者、分享范围 | 任务授权、暂停/取消、必要时人工确认 | 人工完成的步骤不能计为自动完成 | 已有任务草案、预览和暂停等 UI；完整执行授权流程待接通 |
| Task / Workflow / `workflow/Recipe.kt` | 用户目标、参与者、获准来源、已核验消息 | 有序步骤；确定性模板生成的正文与 payloadId | 不定位控件，不操作手机，不自行增加参与者和轮次 | Recipe、PayloadBuilder 已实现；完整运行待验证 |
| 本地小模型 / `model/` | 当前 UI 目标、观察、允许动作、必要引用和预算；实验可加截图 | 有限动作提议和观察中的节点引用；不确定时暂停 | 不直接截图/点击/联网；不决定授权；不改写外发正文；不宣布业务步骤完成 | 实机仅验证 FOCUS_INPUT / PAUSE 定位实验，其他能力未验收 |
| AgentLoop / `agent/AgentLoop.kt` | 当前任务状态、观察、模型提议、工具结果 | 组织 observe → propose → execute → verify 循环；暂停、取消和预算处理 | 不取代模型理解界面，不绕过 Guardrail，不凭模型自述推进完成 | 通用循环仍为骨架；新增固定公开测试题的模型定位与暂存路径，已实测一次定位与暂存；通用调度未验收 |
| Phone Tools / `phone/` | 选定 App；执行时为已授权动作、绑定目标、payloadId | 读取实际窗口/节点/截图；未来执行获准动作并返回客观结果 | 不生成任务正文，不裁定任务是否有权扩大范围，不把点击成功当发送成功 | 单次观察已实测；DeepSeek 固定公开题的 116 字写入/回读成功一次；发送尚未启用 |
| Guardrail / `guardrail/Guardrail.kt` | 提议、任务、最新观察、可信会话证据、当前时间 | ALLOW / DENY / NEEDS_USER 和原因码 | 不调用模型做安全裁决，不通过模型 confidence 证明会话或权限 | 确定性检查已有代码；已通过一次受控写入链；不宣称防护已充分验收 |
| State & Recovery / `state/` | 任务变化、消息证据、执行意图和结果 | 持久状态、来源、journal；恢复时处理不确定性 | 不用模型记忆代替持久状态，不把未知发送结果当失败自动重发 | Room 和恢复逻辑已有；真实提交崩溃恢复尚未实测 |
| 外部 AI App / Kimi、豆包、DeepSeek | 程序构造并经授权送入其会话的正文 | 独立回答、交叉审阅或综合产物 | 其回答不能授权手机动作、换参与者、加轮次或扩大资料分享 | 已观察界面；尚未自动完成一次业务输入/发送/回答抓取闭环 |

截图由 Phone Tools 取得，小模型解释观察并提议下一步，Agent 调度调用。界面理解的准确性、动作执行的正确性、外部 AI 回答的质量是三个不同指标。

## 2. 三款 AI App 的业务角色

角色由当前步骤决定，不固定成“Kimi 规划、豆包执行、DeepSeek 审查”，也不预设哪一家更擅长某种任务。包名/版本属于设备适配配置，业务角色属于 Recipe。

| 步骤角色 | 本轮获准输入 | 期望业务输出 | 业务验收关注点 |
|---|---|---|---|
| INDEPENDENT：独立回答者 | 原问题，不附带同伴回答 | 回答问题，说明假设、依据和不确定项 | 是否回应目标；是否区分事实与推断；不因文风流畅视为事实正确 |
| REVIEW：交叉审阅者 | 原问题及另外两家的第一轮完整产物；自身原会话保留本轮上下文 | 同意点、分歧、遗漏和需核验事实 | 是否引用正确来源、提出有依据的审阅；不能只是重复或迎合 |
| SYNTHESIS：综合者 | 原问题及三份回答、三份审阅 | 最终回答、共识、争议、未解决事项 | 是否保留重要分歧、追溯来源；不以多数投票代替证据 |

默认三家各做一次独立回答、一次交叉审阅，用户指定的一家再综合，合计 3 + 3 + 1。审阅来源固定为第一轮，不能让后执行者多看到先完成的审阅。

上述提示词已在 PayloadBuilder 中实现。外部 App 是否遵循要求、事实是否正确，仍需另做业务质量评估；成功收到回答不代表回答正确。UI 不支持取回完整回答、上下文受限、服务错误等也需独立记录，不能都归为本地小模型失败。

## 3. 能力编号与独立验收

以下编号用于报告和测试用例命名，目前是文档约定，尚未统一写入所有运行时事件；待实现动作已返回能力依赖编号。每项分别记“未实现 / 已实现未验证 / 已有有限实测 / 已达本轮验收标准”；不能用一个总的“POC 成功”覆盖全部能力。

| 能力 ID | 责任主体 | 独立验收方法 / 指标 | 当前证据 |
|---|---|---|---|
| WF-01 步骤与正文来源 | Workflow | 给定同一任务和消息，核对参与者、来源集合、正文和哈希；三方七步及第一轮冻结 | 有实现；相关 JVM 回归已通过 |
| OBS-01 真实观察 | Phone Tools | 已知页面与节点/截图对应；选错 App、锁屏、遮挡、截断须明确失败 | Kimi / DeepSeek 有自身 AccessibilityService 实测；不代表所有页面支持 |
| MODEL-01 有限协议 | 本地模型适配层 | 固定观察，检查结构合法率、节点引用合法率、越权动作/额外正文拒绝率 | 有合法 JSON 实例，未形成统计样本集 |
| MODEL-02 定位与拒答 | 本地模型 | 对每个正例标目标区域；负例标暂停原因。分别统计正确定位、错误定位、正确暂停、过度暂停和超时 | DeepSeek 一份明确输入状态的节点/节点+截图正例；Kimi 语音模式暂停实例 |
| MODEL-03 手机性能 | 本地 backend | 冷加载、单步时延、内存、取消响应；明确硬件、权重、编译配置、输入模式和分母 | 已有时延/PSS记录；没有分位数、取消验收或稳定性结论 |
| AGENT-01 循环与停止 | AgentLoop | 使用可控的模型/工具替身验证步骤上下文、取消、预算、状态修订、不确定结果停止；不据此计算模型识别率 | 生产 AgentLoop 已有替身调度测试；完整设备循环未验收 |
| GUARD-01 执行授权 | Guardrail | 注入格式合法但错 App/会话/payload/过期目标的提议，逐项检查裁决及副作用为零 | 检查代码及 JVM 回归已通过；执行链集成待完成 |
| EXEC-01 手机动作 | Phone Tools | 已授权且目标新鲜时，核对实际聚焦/写入内容/发送证据；分别报告，不把 adb 手动操作计为工具成功 | DeepSeek 2.5.2 固定公开题暂存成功一次；未发送 |
| VERIFY-01 会话与完整回答 | 确定性核验函数，供工具/循环调用 | 相似标题、错角色、截断、生成停顿、错误消息不得变成可转发完整回答；会话证据须匹配当前任务 | 只验证固定空白页身份；历史会话、消息角色和完整性仍未知；不增设第七个 Agent |
| STATE-01 恢复与不重复提交 | State & Recovery | 在发送前后不同阶段中断；核对 journal、状态和副作用次数；不确定提交暂停 | 恢复和提交意图状态转换已有代码并通过 JVM 回归，真实副作用中断实验未做 |
| AI-01 回答质量 | 外部 AI App | 用人工或独立事实依据评价相关性、正确性、来源、审阅价值和综合保真度 | 尚未进行业务回答评测 |
| E2E-01 协作闭环 | 全链路 | 报告自动完成数/总数、人工接管、失败步骤、错会话外发、重复发送、抓取完整性及总耗时 | 尚未完成七步自动运行 |

MODEL-02 的成功不自动满足 GUARD-01 / EXEC-01。只读 ModelExperiment 直接调用 LocalUiModel，不执行动作。另有 SingleExchangeExperiment 经 AgentLoop、Guardrail 和 Phone Tools 实测一次暂存；两类记录分开。

## 4. 怎么定位失败

沿信息流找最早偏离预期的证据，再判断下游是否正确阻止扩散，不直接按最后显示错误的模块归责。

| 现象 | 优先排查 | 需要对照的证据 |
|---|---|---|
| 屏幕有输入入口，观察没有对应节点 | OBS-01 / App 适配 | 采样时刻、前台窗口、是否因切 App 收起输入框、截断和可访问性；不直接认定模型错 |
| 观察正确，模型选错节点或应选却暂停 | MODEL-02 | 同一快照、实际送入模型的候选信息、人工标注、模型提议；候选被过滤也要查适配层 |
| 模型选对，Guardrail 拒绝 | GUARD-01 及证据生产方 | 具体原因码；快照过期、角色未验证等拒绝可能是正确行为，不能为了演示放行 |
| 裁决允许，实际点错/未写入 | EXEC-01 | 执行前的新观察、目标绑定、窗口变化、实际结果 |
| 正文送错接收者或来源 | WF-01 / GUARD-01 / STATE-01 | 冻结来源、recipient、payloadId、哈希与会话绑定 |
| 外部回答错误 | AI-01，同时核对输入 | 实际送达的完整正文和返回内容；先排除串会话、截断或漏传 |
| 回答正确但抓取不全 | VERIFY-01 / Phone Tools | 当前会话、消息角色、原始可访问片段和完整性证据；不要让本地模型补写缺失正文 |
| 重启后重复发送 | STATE-01 / Agent / 执行器 | 执行意图落盘顺序、提交证据、恢复决策、实际发送次数 |

特别是当前定位约 26–37 秒，而 Guardrail 对观察新鲜度限制为 5 秒：这些历史提议不能直接用于点击。已实现 TargetRebinder 纯函数：必须重新观察并逐项比对窗口与整份节点信息，状态不一致则拒绝重新绑定；相同观察也还需 Guardrail 裁决。已接入开发用暂存代码并通过一次实机写入回读，不能仅更新时间戳。这个问题属于模型延迟与执行前核验之间的集成约束。

## 5. 测试记录约定

每份报告明确：能力 ID、任务/步骤或样本 ID、App 版本、模型与 backend 版本、输入模式、预期、实际、裁决/错误原因、耗时、是否真正执行、人工准备/接管部分及证据链接。原始截图和业务正文不默认落盘；需要保留样本时单独脱敏并由用户确认导出。

替身测试证明程序控制逻辑；手动准备页面后的真模型实验验证观察上的定位；完整自动运行才验证自主操作与协作。三类记录分开统计。现有实测见 [模型实验记录](model-experiments/README.md)，后续矩阵见 [验证计划](verification-plan.md)。

## 6. 交接责任：证据由谁生产、谁消费

能力未知时，记录未知，不把工作临时交给另一角色凑出“成功”。本地小模型只做其输入支持的 UI 判断；确定性版本适配规则负责可证实的角色/结构核验，两者可以有不同责任，但不能把人工标定、程序规则的结果记成模型能力。

| 交接 | 生产方责任 | 消费方责任 | 缺失或矛盾时 |
|---|---|---|---|
| 用户 → Workflow | 用户给目标、参与者、分享范围 | Workflow 固定步骤和来源；产生正文、recipient、hash | 缺授权不创建可执行外发任务 |
| Phone Tools → 模型 | 观察实际目标窗口，附版本、时刻、截断/遮挡信息 | 模型只引用所给节点，不猜正文或权限；模型适配层严格解析 | 观察缺失归 OBS；输出无效归 MODEL-01；错误定位归 MODEL-02 |
| 模型 → Agent | 提供有限动作提议或暂停 | Agent 核对当前状态、预算、revision，安排重新观察 | 模型提议不是执行授权；不能用 Codex 的判断替代后计为成功 |
| App 适配 → Guardrail | 从真实结构产生页面、会话和消息角色证据 | Guardrail 独立检查目标、任务、payload、来源和证据 | 不认识页面归适配缺口；正确拒绝不算 Guardrail 缺陷 |
| Guardrail / State → Phone Tools | 授权动作；State 先持久化 intent | 执行器在动作前重验 revision、窗口、节点；只执行获准动作 | 状态变化不执行；已执行但结果未知保留 intent |
| Phone Tools / 核验函数 → State | 提供精确输入回读、用户送达正文、回答角色与完整性证据 | State 检查状态转换、引用和来源；有证据才推进 | performAction=true 不算送达；State 不替核验器猜证据 |
| 外部 AI → 下一轮 Workflow | 外部 App 产生业务原文，可能错误/拒答/超时 | 工具原样提取；Workflow 仅传获准且完整的来源 | 本地模型不得补齐/改写缺片段；业务质量另记 AI-01 |
| 进程重启 → Recovery / Agent | Recovery 从持久状态保留未决副作用 | Agent 重新观察，结果未知不得重发 | 真实事务边界尚未验收；恢复默认暂停 |

核验函数属于版本适配与执行链，不是新增一个 AI 角色。Guardrail 判断“可否做”，核验函数判断“实际发生了什么”，State 判断“这个证据能否推进状态”，三者不能互相替代。

## 7. 不足如何记录

每个问题使用：能力 ID、责任主体、输入证据、预期、实际、最早偏差位置、下游是否阻止、人工参与、影响功能、下一次验证条件。允许“原因尚未确定”，不能只靠最后一个错误码自动归责。分开记录实现缺陷、能力不足、环境故障和样本不足。

当前例子：

- 页面存在隐藏的固定提示导致 profile 拒绝：适配规则缺项，模型尚未运行；已按实测固定文字修正规则，未放开任意未知文字。
- 后台推理 LOW_MEMORY：RUNTIME-01 环境/内存约束，有一次失败；按需加载 projector 后一次成功，仍待稳定性确认。
- 暂存成功后未发送：SEND-01 依赖未确认，主动暂停；不是模型发送失败。

完整未知项、验收方法和受阻功能见 [能力台账](capability-gates.md)；离线回放边界见 [离线回放](offline-replay.md)。

### 调度层的额外交接约束

AgentState 仅暴露读取和按 revision 暂停，生产实现仍为 TaskStore/Room。模型适配器即使返回格式合法对象，Agent 也复查允许动作、接收者、payload 与观察目标；模型耗时后复查状态和预算。工具 ACK 不作为 STAGED 证据，必须已有 State 的精确回读转换。迟到观察/提议/异常不能覆盖更新后的用户状态。相关测试直接运行 AgentLoop，但 backend、工具及持久化均为替身；不宣称真实设备取消和恢复能力已确认。
